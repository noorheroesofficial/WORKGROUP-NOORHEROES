## Flow and persistence boundaries

1. Existing PIN save processing 1650:844 retains original matching, save, offline/API/timeout and count-clearing logic. Its confirmed success close action at index34 is replaced with six flat gated actions: eligibility opens the offer using SWAP; unavailable hardware closes without rendering the offer.
2. Opening requires both the existing success gate 1650:960 and Saved 1650:472. Hardware eligibility is a controlled prototype fixture, not a device probe. Production must perform server success and secure local PIN persistence before this offer.
3. Enable requires Saved, Eligible and not Pending. Pending guards duplicate taps. Swap to the system simulation rather than stacking sheets.
4. After two seconds the controlled success fixture sets simulated Enabled true, clears Pending and closes. Failure clears Pending, leaves Enabled false and swaps to the error sheet.
5. Retry or Enable from the error sheet starts another guarded attempt. Dismiss returns to the original offer. Skip, backdrop and Escape close safely. System Cancel/Escape/backdrop clear Pending and keep PIN available. A late response with Pending false has no effect.
6. Add Child 014 does not exist. Completion, skip, cancellation and unavailable hardware deliberately end with that future destination unmapped; underlying saved PIN remains available. No placeholder route or success claim is added.
7. Selection/capability/outcome variables survive native sheet swaps in the same prototype session. App restart persistence, native lifecycle handling, encrypted preferences and OS enrollment are not implemented by Figma. Production interrupted authentication must clear transient busy state and retain the PIN fallback.

Biometric enrollment is local and optional. No network/empty-list state is applicable to this offer; the existing PIN save still handles network failures. Neither biometric templates nor raw PINs are held in this prototype. No data is sent to a server by these Figma actions.
